# Infrastructure & Deployment Audit — FinCopilot 2.0

**Date:** 2026-07-05 · **Scope:** Docker Compose (local), Railway single-container deploy (`start.sh`, Dockerfile), Alembic migration chain, health/shutdown behavior, observability, backup/recovery, secrets, local dev friction · **Method:** full read of `docker-compose.yml`, `backend/Dockerfile`, `backend/start.sh`, `celery_app.py`, `config.py`, `main.py`, `logging.py`, retrieval/ingestion code, and all 11 migration files; git history checked for committed secrets and for the origin of the single-container merge (`ac17631`). Report-only; no code changed.

Deployment constraints taken as given (not re-litigated): uvicorn + Celery share one Railway container because Railway services have no shared filesystem; `--concurrency=1` and `RERANK_ENABLED=False` were deliberate memory decisions; port 8000 is intentionally fixed (`008a44c`).

Overlap note: `docs/audits/backend-audit.md` (2026-07-04) already covers several adjacent code-level findings (temp-file leak, missing `task_acks_late`, ingestion idempotency, dual HNSW index, `.dockerignore`). This audit cross-references those rather than re-arguing them, and focuses on the infra verdicts they roll up into.

---

## TLDR

1. **Memory: no headroom at 1 GB for either change.** Steady state is roughly 500–700 MB (uvicorn ~250–350 MB + Celery parent ~150–200 MB + one prefork child ~100–200 MB), and a single large-file ingestion can transiently add several hundred MB more because `_build_chunks` materializes the entire document as a Python list of token ints plus a same-length offsets list (`ingestion.py:164-176` — a 50 MB text file is ~12 M tokens ≈ 400–900 MB of list overhead). Re-enabling the reranker adds ~300–400 MB steady to the API process (torch CPU runtime ~150–250 MB + MiniLM-L6 cross-encoder ~90 MB fp32 + tokenizer/buffers); concurrency=2 adds ~100–200 MB steady **and doubles the worst-case transient spike**. Neither fits in 1 GB. At 2 GB, the reranker is the safer re-enable (bounded, lazy-loaded, biggest quality win); concurrency=2 stays risky until the chunker's O(tokens) memory is fixed.
2. **Every Railway deploy hard-kills in-flight work.** `start.sh` runs bash as PID 1 with Celery backgrounded via `&` and no `trap`/`wait`/`exec` — PID-1 bash has no SIGTERM handler, so Railway's SIGTERM is ignored and everything gets SIGKILL after the grace period. uvicorn never drains connections, Celery never warm-shuts, and because acks are early (no `task_acks_late`, per backend audit), an ingestion caught mid-deploy is lost forever with the document stuck in `processing`.
3. **Health is blind to half the container.** `/api/health` returns a static `ok` with no DB, Redis, or Celery check (`app/api/router.py:6-8`). The historical failure mode — OOM killer taking out one process inside the container — leaves the container "healthy" while ingestion silently queues forever. Nothing restarts a dead worker; `set -e` doesn't watch background jobs.
4. **Local Compose contradicts the single-worker constraint the prod merge exists to satisfy.** `docker-compose.yml` runs the `api` container with the Dockerfile CMD (`start.sh` → its own worker) **plus** a separate `celery-worker` service — two queue consumers — while uploads are written to `/tmp` inside the API container (`documents.py:84`), which is not the shared `uploads` volume. Any task grabbed by the second worker hits `FileNotFoundError` — the exact bug commit `ac17631` fixed in production, still live locally.
5. **The migration chain cannot be replayed against a populated database and is irreversible below 0006.** `1cfb79155de6` adds `conversation_id NOT NULL` with no server default (fails on any non-empty `documents`/`document_chunks`), and its downgrade both calls `op.drop_constraint(None, ...)` (raises) and recreates the HNSW index without an operator class (Postgres rejects it). This matters most in combination with finding 6.
6. **There is no backup strategy in evidence and no sign a restore has ever been tested** — while the Postgres DB is the *only* copy of user data (source files live on ephemeral disk and are deleted or lost on redeploy; chunks can't be re-derived). A restore would also have to navigate pgvector extension availability and the non-replayable migration chain.
7. **Observability is Railway's log viewer plus LangSmith (if the key is set).** No error tracking, no uptime monitoring, no alerting, no log aggregation. A production failure surfaces when a user reports it, or when someone happens to open the Railway logs.
8. **Secrets are clean in git** (`.env` ignored and never committed) but local Docker builds bake `backend/.env` and `venv/` into image layers because there is no `.dockerignore` (`Dockerfile:5` `COPY . .`). Railway builds from git, so production images are clean — the risk is any locally built image being pushed anywhere.

## Memory budget (question 1, worked through)

**Container:** 1 GB Railway service running three processes: uvicorn, Celery prefork parent, 1 Celery child. Postgres and Redis are external Railway services — not in this budget.

**Steady state:**

| Component | Estimate | Basis |
|---|---|---|
| uvicorn/FastAPI process | ~250–350 MB | imports langgraph, langchain-core, openai, SQLAlchemy, numpy; tiktoken cache loads on first chat |
| Celery parent | ~150–200 MB | same app import graph (pypdf, bs4, tiktoken imported at task-module level) |
| Celery child (×1) | ~100–200 MB private | forked COW, grows after first ingestion (tiktoken `cl100k_base` ≈ 80 MB loads here) |
| **Total steady** | **~500–700 MB** | leaves ~300–500 MB headroom |

**Transient spikes (the real constraint):** `_build_chunks` (`app/tasks/ingestion.py:164-176`) does `enc.encode(full_text)` into a Python list and then builds a `token_char_offsets` list of the same length, decoding **every token individually**. Python list-of-int overhead is ~30–40 bytes/token, so a text-heavy upload at the 50 MB limit (`MAX_UPLOAD_BYTES`, and the chat path allows 100 MB per the backend audit) is ~12 M tokens → **400–900 MB transient in the child**, on top of pypdf's own buffers and the full extracted text held twice. A typical 10-K (~1 MB text) is harmless (~10 MB); the ceiling case is one large CSV/TXT/HTML upload.

**Reranker (`RERANK_ENABLED=True`):** `cross-encoder/ms-marco-MiniLM-L-6-v2` is ~22.7 M params ≈ 91 MB fp32, but the dominant cost is importing torch CPU (~150–250 MB RSS) plus tokenizer/buffers — **~300–400 MB added to the uvicorn process, permanently, after the first retrieval** (lazy load, `retrieval.py:24-35`). Inference itself is negligible (candidate pool is `top_k × 3 = 15` pairs). Net: steady state goes to ~850–1,100 MB *before* any ingestion runs. **Not safe at 1 GB.**

**Concurrency=2:** adds a second child (+100–200 MB steady) and, worse, allows two simultaneous ingestion spikes. Even without the pathological case, two concurrent PDF parses + embedding batches can clear the remaining headroom. **Not safe at 1 GB, and marginal even at 2 GB until the chunker spike is fixed.**

**Verdict:** the app is still near the ceiling; both mitigations remain load-bearing. The realistic upgrade path is: (a) bump the Railway service to 2 GB, (b) re-enable the reranker first — its cost is bounded and steady, and hybrid-only ranking is the bigger quality gap, (c) only consider concurrency=2 after `_build_chunks` streams token offsets instead of materializing them (that fix alone also removes today's worst OOM vector at concurrency=1). Cheap independent win: set `worker_max_tasks_per_child` (e.g. 20) so leak accumulation in the long-lived child resets periodically.

## Answers to the specific questions

1. **Memory headroom** — No. See the worked budget above: ~500–700 MB steady of 1,024 MB, with single-ingestion transients that can already approach the ceiling due to the chunker's O(tokens) list materialization. Reranker ≈ +300–400 MB steady; concurrency=2 ≈ +100–200 MB steady plus doubled spike exposure. Either change needs 2 GB; reranker first if forced to choose.
2. **Config drift** — Four production-relevant drifts found: dual queue consumers + non-shared `/tmp` in local Compose (High), concurrency 1-vs-2 between CLI and code (Medium), CORS excluding Vercel previews (Medium), and the `APP_ENV`/JSON-logging + env-var-fallback class (Medium, NV). Plus vestigial uploads volume, dead requirements.txt, stale `.env.example` (Low).
3. **Migration safety** — Chain is 11 revisions with head **0011**, not 0012 as briefed (no `0005`; `1cfb79155de6` fills the gap — verify `alembic_version` on Railway). Nothing pending is destructive, but the chain is **irreversible below 0006** and **non-replayable against populated data** (`1cfb79155de6`), and 0011-style persisted columns rewrite the whole table under exclusive lock. Rule to adopt: dump before every prod `alembic upgrade`.
4. **Health & shutdown** — Both broken in the ways that matter: health is a static 200 that can't see a dead worker, and shutdown is SIGKILL-by-default because PID-1 bash never forwards SIGTERM; with early acks, deploys can silently destroy in-flight ingestions. These two are the highest-leverage fixes in this report.
5. **Observability** — Railway log viewer + LangSmith (if configured). No error tracking, uptime monitoring, or alerting; failures surface via users.
6. **Backup/recovery** — Nothing in the repo; Railway-side state NV but there is no restore runbook and no evidence of a drill, against a DB that is the only copy of non-recoverable user data.
7. **Secrets** — Clean in git (ignored, never committed, never logged; middleware logs method/path/status only). Two residual risks: no `.dockerignore` means locally built images contain `backend/.env`, and the mangled `.gitignore` line means protection rests on the generic `.env` rule alone. Railway/Vercel storage itself NV, presumed standard.
8. **Local dev friction** — `restart-frontend.bat` noted as a known Windows quirk; it isn't checked into the repo at all, which is the only thing actually worth changing. `kill-port` as a `predev` hook is the cleaner cross-platform equivalent if desired.

## What's solid

- **The single-container merge is the right call for Railway's constraints and is well-documented in history** — `ac17631` states the shared-filesystem rationale; the memory mitigations (`--concurrency=1`, lazy-loaded reranker behind a flag with a load-failure latch, `RERANK_ENABLED` comment explaining the 1 GB OOM) all carry their reasoning in code comments.
- **The reranker quarantine is genuinely defensive**: torch is only imported inside the flag check (`retrieval.py:252-256`), load failure is latched so it can't retry-loop, and rerank failure falls back to hybrid order instead of erroring the request.
- **Local infra hygiene is above average**: Postgres and Redis both have real healthchecks with `depends_on: condition: service_healthy` gating, pinned images (`pgvector/pgvector:pg15`, `redis:7-alpine`), and named volumes for data.
- **Migration craftsmanship recovered well from the autogenerate incident**: 0006 documents exactly what `1cfb79155de6` broke and why each restoration exists; 0007 correctly uses `autocommit_block()` for `CREATE INDEX CONCURRENTLY` with idempotent `IF NOT EXISTS`; 0002/0010 use partial indexes appropriately.
- **Secrets discipline in the application layer is good**: startup fails fast on missing required keys with a clear log (`main.py:24-36`), config is a single typed settings object, request logging never touches headers or bodies, and git history contains no `.env` at any point.
- **Structured logging foundation is in place** (structlog + contextvars request IDs + `X-Request-ID` response header) — when a log drain or Sentry is added, the plumbing is ready.
