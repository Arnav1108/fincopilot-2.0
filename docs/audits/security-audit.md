# FinCopilot 2.0 — Cross-Cutting Security Audit

**Scope:** Authorization / tenant isolation, secrets, SSRF, file-upload validation, injection, CORS, rate limiting / abuse, dependency risk, Clerk configuration. Report-only; nothing was changed.

**Method:** Read every FastAPI route, every LangGraph tool that reads by ID, the agent executor/tool-selector, the ingestion pipeline, Clerk auth + webhook verification, the frontend middleware/config, and `.env` / git tracking. Grepped for raw SQL, hardcoded secrets, and per-user rate limiting.

---

## TLDR — ranked by exploitability × impact

1. **No per-user rate limiting on any expensive operation (cost/OOM abuse).** `/conversations/{id}/stream` (LLM calls), `/documents/upload`, and every agent tool (OpenAI embeddings, Serper, SEC EDGAR) have no per-user quota. The only limiter is a *global* 10-req/sec EDGAR bucket (`rate_limiter.py`). One authenticated user scripting the chat endpoint can burn the shared OpenAI/Serper budget and OOM-kill the 1 GB Railway container. **Highest real-world risk** — trivially exploitable by any signed-up user, direct financial + availability impact.

2. **Upload reads the entire file into memory *before* the size check → OOM DoS.** Both `documents.py:54` and `chat.py:102` do `await file.read()` (full body into RAM) and only *then* compare against the 50 MB / 100 MB limit. A few concurrent large uploads exhaust the 1 GB container. The byte limit does not protect you because the memory is already spent by the time it's enforced.

3. **Live secrets sit in `backend/.env` (real OpenAI `sk-proj-` key, Clerk secret, LangSmith, Serper).** The file is correctly git-ignored and **never committed** (verified — only `.env.example` is tracked), so there is no git-history leak. But these are active production keys on disk; the OpenAI key in particular is a real, spendable credential. Rotate anything that has been shared/opened, and confirm Railway injects them as env vars rather than shipping this file in the image.

4. **File-type validation is extension-only; no magic-byte/content check.** `documents.py:46` and `chat.py:_infer_file_type` trust the filename extension. A `.pdf` that is actually a zip bomb / malformed PDF reaches `pypdf`/`BeautifulSoup` unguarded, and there is no page-count cap — a decompression-bomb PDF can pin CPU/RAM in the single Celery worker and stall all ingestion.

5. **`/documents/upload` never verifies the `conversation_id` belongs to the caller.** `upload_document` (`documents.py:35`) takes `conversation_id` as a form field and writes a `Document` with the attacker's `user_id` but an arbitrary conversation. Impact is limited (retrieval is user-scoped, so it can't leak into the victim's view) — it's a missing server-side ownership check / cross-conversation write, not a data-exfil path. Note the parallel `chat.py` stream endpoint *does* check ownership, which makes the gap in `documents.py` clearly an oversight.

6. **`python-jose 3.3.0` (the JWT verifier) is unmaintained with known CVEs.** CVE-2024-33664 (JWE decompression DoS) and CVE-2024-33663 (algorithm confusion) affect it. Algorithm confusion is mitigated because `auth.py:44` pins `algorithms=["RS256"]`, but the library is EOL and validates every request's token.

**Solid (details below):** tenant isolation on all ID-based reads is enforced server-side; user_id/conversation_id are injected into tools and *overwrite* any LLM-supplied value; retrieval is filtered by `user_id AND conversation_id`; CORS is scoped (not wildcard); Clerk webhook uses real Svix signature verification; no raw-SQL string concatenation anywhere; prompt injection cannot cross tenants.

## What's solid

- **Tenant isolation on every ID-based read is enforced server-side.** `conversations.py`, `portfolios.py`, `memories.py`, `profile.py`, and `documents.py` GET/PATCH/DELETE all filter by `user_id` (portfolios via the `_get_portfolio_or_404` helper; holdings are re-scoped through their parent portfolio). No route trusts a client-supplied owner id.
- **Agent tools cannot be steered across tenants.** In both `tool_selector.py:112-116` and `executor.py:44-48`, `user_id` and `conversation_id` are written from the authenticated `AgentState` *after* the LLM's input dict is built, so any value the model (or an injected document) tries to supply is overwritten. `retrieval.py:112-118` and `_fts_query` filter on `user_id AND conversation_id`; user-supplied `doc_ids` are intersected against the caller's own `available_documents` (`executor.py:52-63`).
- **Prompt injection stays within the victim's own context.** Because tool identity is injected server-side and retrieval is user-scoped, a malicious document can at worst trigger tool calls (e.g. an EDGAR fetch → cost) inside the *same* user's conversation. It cannot read or write another user's data. The residual is cost/abuse, already covered by finding #1.
- **CORS is scoped, not wildcard.** `main.py:43-49` uses `settings.ALLOWED_ORIGINS` (`localhost:3000` + the Vercel origin) with `allow_credentials=True`; no `"*"` origin.
- **Clerk webhook verification is real.** `webhooks.py:35` verifies the Svix signature over the raw body and rejects when `CLERK_WEBHOOK_SECRET` is unset — no unauthenticated user create/delete.
- **No SQL injection surface.** All queries use SQLAlchemy expression objects; the only literal SQL is static DDL in Alembic migrations (`CREATE EXTENSION`, `CREATE TYPE`, index DDL) with no interpolated user input. The FTS `@@` operator is parameterized.
- **Secrets are not committed.** Git tracks only `.env.example`; `backend/.env` is git-ignored and absent from history.
- **No secrets in `NEXT_PUBLIC_*`.** The frontend only exposes `NEXT_PUBLIC_API_URL` and the Clerk *publishable* key (public by design); the JWT is fetched per-request via Clerk `getToken()` and sent as a Bearer header.
- **Frontend auth has a layout-level backstop.** `app/(shell)/layout.tsx` calls `await auth()` and redirects unauthenticated users, and `clerkMiddleware()` only supplies auth context. Even so, the real protection is the backend — every `/api/*` route depends on `clerk_auth`, so a missed page-level check cannot expose data.
- **Clerk middleware isn't over-granting.** The stripped-down `clerkMiddleware()` performs no route authorization itself; it doesn't widen access, it just enables `auth()`. The broad `matcher` only controls where the context is attached, not what's permitted.
