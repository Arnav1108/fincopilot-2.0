# Backend Audit — FinCopilot 2.0

**Date:** 2026-07-04 · **Scope:** `backend/` (FastAPI + SQLAlchemy 2.0 async, Postgres/pgvector, Celery + Redis, single Railway container via `start.sh`) · **Method:** full read of all route handlers, tasks, tools, services, models, schemas, and all 11 migration files; enum/string bind behavior verified by compiling statements against the installed SQLAlchemy. Report-only; no code changed.

All file paths are relative to `backend/`.

Deployment constraints taken as given (not re-litigated): uvicorn + Celery share one container because Railway offers no shared filesystem between services; Celery `--concurrency=1` is a deliberate memory tradeoff; `postgresql+asyncpg://` prefix is required.

---

## TLDR

1. **One cross-tenant write hole: `POST /api/v1/documents/upload` never checks that `conversation_id` belongs to the caller** (`app/api/v1/documents.py:38` — the doc is created against any conversation UUID with no ownership or existence check). Every other conversation/document/portfolio/memory endpoint is correctly user-scoped, and chunk retrieval is double-scoped by `user_id` *and* `conversation_id`, so the blast radius is data pollution plus a conversation-ID existence oracle rather than data disclosure — but it's the exact class of bug this app can't afford.
2. **The 10-K-only extraction discipline does NOT extend to 10-Qs.** `document_finder.py` accepts `filing_type="10-Q"` down the SEC route, but the section extractor is hardcoded to `<TYPE>10-K` (`app/tools/document_finder.py:191`), so any 10-Q fetch misses, hits the fallback at line 200 — `extracted = raw_text` — and embeds the full 30–50 MB submission file. That fallback also silently re-introduces embedding overload for 10-Ks whenever the marker doesn't match. The fetch year is likewise *not* always explicit: `year` is `Optional` (`app/schemas/tools/document_finder.py:14`) and when omitted the duplicate check matches a filing from *any* year — the known collision is still live.
3. **Celery ingestion is not restart-safe and not idempotent.** No `task_acks_late` is set (`app/celery_app.py:12-22`), so a worker restart mid-ingestion silently drops the task and leaves the document in `processing` forever; re-delivering the task would duplicate every chunk (no cleanup, no unique constraint on `(document_id, chunk_index)`); and the temp file is only deleted when retries are exhausted — **never on success** (`app/tasks/ingestion.py:358`), so every successfully ingested upload leaks its file onto the container disk.
4. **Two real event-loop blockers:** the Tavily call in document_finder's web route is synchronous HTTP on the loop (`app/tools/document_finder.py:221` — `news_fetch.py` offloads the same client correctly), and the LangSmith `read_run` in the chat stream is a sync HTTP client called from async code, preceded by an unconditional `await asyncio.sleep(1.0)` that adds a flat second to **every** chat turn (`app/api/v1/chat.py:360-364`).
5. **Metadata-filtered retrieval silently returns nothing:** `document_retrieval._apply_filters` reads `meta.get("ticker")` and `meta.get("fiscal_year")`, but the retrieval service writes those keys as `doc_ticker`/`doc_filing_date` and nothing ever writes `fiscal_year` (`app/tools/document_retrieval.py:58-62` vs `app/services/retrieval.py:59-64`). Any agent step that passes a ticker filter gets zero chunks with no error.
6. **Migration reality differs from the brief:** the chain is intact but is 11 revisions with head at **0011**, not 0012 — there is no `0005` (the hash-named `1cfb79155de6` sits between 0004 and 0006) and no 0012 file exists (needs verification against the deployed `alembic_version` table). Two HNSW indexes exist on the same column (0006 + 0007), doubling index maintenance on every chunk insert, and 0011 introduces an `idx_` prefix in a codebase that otherwise uses `ix_` — the same naming-drift family as the old `ix_conversations_deleted_at_null` typo.

## What's solid

- **Authorization everywhere else is genuinely well done.** Conversations (list/rename/delete/messages/documents/chunks) all filter on `user_id` in the WHERE clause rather than fetch-then-compare; portfolios centralize the check in `_get_portfolio_or_404` and holdings verify both the portfolio ownership *and* the holding→portfolio linkage (`portfolios.py:157-178`); memories and profile are user-scoped; and the retrieval service enforces `user_id` **and** `conversation_id` at the chunk level (`retrieval.py:112-115`), so even the upload hole above can't leak content across tenants. Defense in depth is real here.
- **The agent executor injects identity server-side.** `user_id`/`conversation_id` are overwritten from authenticated state for every tool call (`executor.py:43-47`) — the LLM can never choose whose data a tool touches. `doc_ids` from the model are validated against the conversation's own document list (`executor.py:52-63`).
- **Webhook handling is correct:** raw-body Svix signature verification before parsing, `on_conflict_do_nothing` for user.created, and the auth upsert deliberately avoids clobbering webhook-set fields (`auth.py:64-65` comment matches the code).
- **Async hygiene is mostly right:** yfinance goes through `run_in_executor` with a bounded semaphore (`financial_data.py:100`, `portfolio_analysis.py:64-77`, `company_comparator.py:151`), the cross-encoder through `asyncio.to_thread`, news_fetch offloads Tavily, and all EDGAR/Serper HTTP is httpx-async. The two blockers found (document_finder Tavily, LangSmith read_run) are deviations from an established good pattern, not the norm.
- **Secrets discipline holds.** No API key or secret is ever logged (verified by grep across all log calls); health endpoints return only status/version; config lives in one pydantic-settings singleton with startup validation that fails fast on missing required keys (`main.py:24-36`); `.env` is git-ignored.
- **Migrations are unusually disciplined for a young project:** every revision has a real, tested-looking downgrade; 0006 is a careful repair of the autogenerate accident with an honest docstring; 0007 handles `CREATE INDEX CONCURRENTLY` correctly via `autocommit_block()` with the reasoning documented; the soft-delete partial index and the `(conversation_id, user_id)` composite match the actual query shapes in the code.
- **The 1 GB memory constraint is managed deliberately and documented in-code:** rerank disabled with a comment explaining the OOM (`config.py:32-35`), lazy torch import, `worker_concurrency` comment explaining the Railway cpu_count fork bomb (`celery_app.py:18-21`).
- **The SSE status stream subscribe-before-query race fix** (`documents.py:147-150`) shows the right instinct — it just needs to be propagated to `document_finder._ingest_and_wait`.
- **Hybrid search is implemented carefully:** FTS failure falls back to pure vector, min-max normalization guards the degenerate equal-scores case, and the generated `content_tsv` column + GIN index push tokenization into Postgres.
- **Structured logging foundation is good** — structlog with contextvar merging, request-ID middleware with `X-Request-ID` response header, JSON renderer in production. The gaps are level tuning and correlation breadth, not architecture.

## Suggested fix order

1. Ownership check on `documents.py` upload (small, closes the only cross-tenant write).
2. Ingestion temp-file deletion + chunk idempotency + `task_acks_late`/time limits (one PR; they interlock).
3. `<TYPE>` extraction parameterization + kill the full-file fallback; make `year` required for SEC filing types.
4. The two event-loop blockers + drop the 1 s LangSmith sleep from the hot path.
5. Retrieval filter key fix (`doc_ticker`/`doc_filing_date`).
6. `.dockerignore`, duplicate HNSW index drop, error-message sanitization, logging level pass.
